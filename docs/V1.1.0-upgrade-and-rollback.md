# V1.1.0 升级与回滚说明

## 发布前置条件

1. 在 1Panel 核验当前线上容器镜像和 Git Commit，将该实际 Commit 追认为 `v1.0.0`。
2. 对 PostgreSQL 数据卷执行完整备份，并在隔离环境完成恢复验证。
3. 在隔离副本执行 `V1.0.0 → V1.1.0` 迁移、固定 E2E、对账和三角色冒烟。
4. 仅当 `v1.1.0-rc.1` 验收通过后，才创建 `v1.1.0` Tag 和正式 Release。

## 1Panel 升级

`.env` 固定版本：

```dotenv
APP_VERSION=1.1.0
```

拉取并启动：

```bash
docker compose -f docker-compose.1panel.yml pull
docker compose -f docker-compose.1panel.yml up -d
docker compose -f docker-compose.1panel.yml ps
curl -fsS http://127.0.0.1:${WEB_PORT:-8080}/api/health
```

API 容器启动时只执行向前迁移和幂等种子；不会重置数据库，也不会覆盖已修改的账号密码。

## 发布后检查

- `/api/health` 返回成功。
- `/api/system/version` 返回 `1.1.0`、构建时间和实际 Git Commit。
- ADMIN、WAREHOUSE、PRODUCTION 三个角色均可登录。
- 创建一张不提交的草稿，确认列表、编辑和删除正常。
- 执行 `pnpm --filter @inventory/api inventory:reconcile` 或管理员对账接口，结果必须为一致。
- 检查 API、Web、PostgreSQL 日志中没有迁移错误、SQL 堆栈或持续 5xx。

## 回滚

本次迁移涉及库存维度和权限数据，正式回滚不执行逆向迁移。

1. 立即停止业务写入。
2. 在 1Panel 停止 V1.1.0 API/Web 容器。
3. 恢复维护窗口开始前的 PostgreSQL 完整备份。
4. 将 `APP_VERSION` 切回已核验的 `1.0.0` 镜像标签。
5. 重新启动并执行健康检查、三角色登录和库存余额抽查。
6. 在发布记录中填写失败步骤、日志、恢复时间和数据恢复点。

严禁只回滚应用镜像而继续使用已经完成 V1.1.0 迁移的生产数据库。
